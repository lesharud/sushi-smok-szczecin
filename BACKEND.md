# Backend / границы текущего этапа

Сайт использует структурированный каталог `src/shop/catalog.json` и типизированный `OrderRepository`. Сейчас подключён только demo-adapter: он не отправляет заказы ресторану, не списывает деньги и создаёт номера `TEST-*`. Конфигурация Supabase Auth **не включает реальные заказы автоматически**.

## Supabase Auth

Скопировать `.env.example` в `.env.local`, указать URL собственного проекта и публичный anon/publishable key в `VITE_SUPABASE_ANON_KEY`, перезапустить Vite. Service role никогда не попадает в браузер. В Supabase включить Email provider и email confirmation, добавить домен сайта и `/account` в Redirect URLs, настроить SMTP и rate limits. Регистрация/вход/выход используют настоящий SDK. Без ключей страницы объясняют недоступность аккаунтов; локальная имитация паролей не используется. Реальная интеграция не проверена: ключи не предоставлены.

Профиль, адреса и история в нынешнем UI относятся к текущему устройству и прямо так подписаны, даже после входа. Облачную синхронизацию необходимо подключить отдельно к таблицам с RLS; не смешивать локальную гостевую историю с заказами пользователя.

## База данных

`supabase/migrations/202609140001_restaurant.sql`: categories, products, profiles, addresses, orders, order_items. Каталог доступен на чтение; профиль и адреса ограничены auth.uid(); заказы доступны владельцу только на чтение. Публичная запись заказов, цен и статусов закрыта. Применить SQL в своём проекте, затем `supabase/seed.sql`. Seed не перезаписывает правки владельца. `node scripts/seed-catalog.mjs` обновляет seed из JSON.

## Настоящий заказ — следующий этап

Заменить demo-реализацию `OrderRepository.submit` серверным endpoint. Клиент передаёт productId/quantity, контакты, способ получения и idempotency key. Сервер обязан:

1. Валидировать контакты, адрес, район доставки, расписание, максимальные количества; получить цены и доступность из БД, рассчитать доставку и итог.
2. В одной транзакции записать order + order_items со снимками названий и цен, дедуплицировать idempotency key. Нельзя принимать итог клиента как источник истины.
3. Отправить заказ в канал ресторана и вернуть подтверждённый статус. Оценку времени и номер реального заказа возвращает сервер.
4. Для гостя вернуть криптографически случайный receipt token и ограничить доступ к чеку. UUID сам по себе не заменяет авторизацию. Для аккаунта использовать RLS.
5. Если нужны онлайн-платежи, создать платёжную сессию на сервере. Статус paid ставить только после проверенного webhook. Никаких карточных реквизитов в текущей форме нет.
6. Предусмотреть rate limiting, мониторинг, уведомления, журнал ошибок, правила возврата, согласованную политику хранения персональных данных.

До этого оставить demo-notice и адаптер demo. Не достаточно просто скрыть предупреждение. Не выдумывать тариф, минимальный заказ, область доставки, сроки или способы оплаты.

## Хранение на устройстве

Корзина: localStorage, только productId/quantity. Полный последний тестовый чек — sessionStorage этой вкладки. История до 50 записей — localStorage без имени/телефона/e-mail/адреса/примечания по умолчанию. Только явный checkbox разрешает запомнить персональные данные. В профиле есть удаление данных и истории. Пароли не сохраняются кодом приложения. Supabase SDK самостоятельно управляет своей сессией, когда подключён.

## Развёртывание

`SITE_URL=https://ваш-домен npm run build` создаёт HTML главной, меню, категорий и блюд, canonical/OG/sitemap. Сервисные страницы noindex. Настроить fallback неизвестных SPA-путей на `/index.html` (пример Netlify `_redirects` уже есть); для Nginx использовать `try_files $uri $uri/index.html /index.html`. Не кэшировать будущий API заказов. Manifest и иконки готовы, service worker намеренно не добавлен, чтобы не выдавать устаревший checkout за работающий offline.
