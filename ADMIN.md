# Этап 2 — Restaurant Admin / Kitchen

Публичные покупатели по-прежнему оформляют заказ без аккаунта. Сотрудники используют отдельный `/admin/login`. Дизайн публичного сайта сохранён.

## Архитектура

- Supabase Auth: email/password, восстановление и обновление сессии, локальный выход на этом устройстве. Регистрации в интерфейсе нет.
- `staff_profiles`: `user_id → auth.users`, роль `admin` / `staff`, флаг `active`. Наличие Auth-пользователя само по себе не даёт доступа. Метаданные, которые пользователь может изменить сам, для авторизации не используются.
- Браузер получает только publishable key и свою Auth-сессию. Supabase проверяет JWT, PostgreSQL RLS ограничивает чтение. Прямые записи таблиц запрещены браузеру; узкие SECURITY DEFINER RPC проверяют роль и входные данные.
- Staff: заказы, детали, кухня, статусы. Admin: дополнительно меню и настройки. Управление сотрудниками пока через Supabase Dashboard, без лишней панели пользователей.
- `staff_change_order_status`: блокировка строки, ожидаемый предыдущий статус, только последовательные переходы; отмена возможна до завершения. `order_status_events` сохраняет автора/время/переход без копирования контактов клиента.
- Изменения товаров/настроек используют `updated_at` для защиты от перезаписи изменений другого администратора.
- Guest RPC Этапа 1 не изменён. Стоимость и доступность проверяются в БД. Старые заказы сохраняют snapshots.

## Автоматическое обновление

Orders/Kitchen выполняют реальные запросы через Supabase каждые 5 секунд. Запросы идут последовательно, при ошибке повторяются; восстановление также происходит при focus/online. Видны время последнего обновления и ошибка устаревших данных. Счётчик новых заказов обновляется независимо от фильтра. Это polling, **не Supabase Realtime**. Дополнительной публикации заказов/PII, replication или WebSocket policies не требуется. На мобильном фоне таймеры могут замедляться браузером; после возврата данные обновляются.

Рабочий список: 50 заказов на страницу; кухня: 200 на страницу, от старых к новым, с явной пагинацией. История: номер, статус, дата в часовом поясе устройства (подписано в интерфейсе). Времена заказов показываются по Europe/Warsaw. Включение звука не реализовано.

## Облачное подключение — проверено через CLI

Supabase CLI связан с существующим production-проектом, Vercel CLI — с `sushi-smok-szczecin`. Проверена migration history: `202609150001` и `202609160001` совпадают local/remote. **Повторно эти миграции не применять.**

```bash
supabase migration list
vercel project inspect
```

Миграция Этапа 2 добавочная. Она сохраняет заказы и каталог, не включает доставку. Seed повторять не нужно.

## Первый администратор

В облаке найден один существующий подтверждённый Auth-пользователь; ему назначен активный `admin` через CLI и `scripts/bootstrap-admin.sql`. Пароль не изменён. Публичная регистрация отключена — проверено через Auth API.

Для нового окружения однократный bootstrap запускается так:

```bash
supabase db query --linked --file scripts/bootstrap-admin.sql
```

Скрипт намеренно останавливается, если Auth-пользователей не ровно один или email не подтверждён. Он не создаёт пользователя и не выбирает случайный аккаунт. В уже настроенном проекте повторять bootstrap не требуется. При нескольких пользователях назначать роль нужно адресным SQL после проверки конкретного UUID, без вывода паролей/токенов.

Чтобы отозвать доступ, установить `staff_profiles.active=false` для конкретного сотрудника. Проверка роли происходит в базе при запросах; UI обновляет членство каждые 10 секунд. Logout завершает сессию на текущем устройстве. Для немедленного отзыва прав при ещё действующем JWT используется `active=false`.

## ENV — локально и в Vercel после согласования

Существующие **server-only** значения остаются:

- `SUPABASE_URL`
- `SUPABASE_SECRET_KEY` — никогда не `VITE_*`.

Локальные **публичные** значения уже получены через CLI и записаны в `.env.local` (права 600). Для безопасной повторной настройки:

```bash
node scripts/configure-admin-env.mjs
```

Скрипт сверяет linked Supabase с server URL и не печатает ключи. Переменные:

```dotenv
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

URL совпадает с серверным SUPABASE_URL. Publishable key взять в Supabase Connect / Settings → API Keys → Publishable key. Не путать с `sb_secret_...`. Клиент принимает только `sb_publishable_` и не использует service-role. Build-time проверка дополнительно отклоняет server-secret и service_role JWT в любых VITE-переменных, не выводя значения. Эти значения встраиваются при build; после их изменения требуется новая сборка. Если их нет, `/admin/login` показывает сообщение о незавершённой настройке; Guest Checkout продолжает работать.

Добавление отсутствующих публичных значений в **Vercel Production — только после подтверждения владельца**:

```bash
node scripts/configure-admin-env.mjs --vercel-production
```

Команда проверяет имя проекта `sushi-smok-szczecin`, не перезаписывает существующие ENV и не запускает deployment. Обе публичные переменные добавлены в Production через CLI с разрешения владельца. Server secrets и VITE_SITE_INDEXABLE не изменялись.

`SITE_URL` и `VITE_SITE_INDEXABLE` работают как раньше. Admin всегда получает noindex. Публичного sitemap для Admin нет.

## Управление меню

Admin может изменить название, описание, существующую категорию, цену (ввод в zł, хранение в groszy), доступность. Изображения, product IDs, slug и составные метаданные не переписываются. Добавление/удаление товаров и категорий не входит в этот этап.

Публичный `/api/catalog` возвращает только id/name/description/category/price/availability. Клиент обновляет существующие карточки каждые 15 секунд и при возвращении на вкладку, без изменения дизайна. Если запрос не удался, остаётся последний каталог с сообщением о проверке цен при оформлении. Неизвестные/удалённые в БД товары нельзя оформить; backend всегда является источником истины. Изменение availability выключает существующие Add-кнопки; checkout блокирует известные недоступные позиции. Неопределённая повторная отправка прежнего заказа продолжает использовать исходный ключ идемпотентности.

## Настройки

Используются только поддерживаемые поля: ordering_enabled, delivery_enabled, delivery_fee_grosz. Доставку включать только после подтверждения тарифа и процесса обслуживания адресов рестораном. Настройки минимальной суммы, зон, расписания или уведомлений не добавлены. Завершённые заказы не изменяются при отключении приёма новых.

## Проверки

```bash
npm run build
npm run test:backend
npm run test:e2e
npm run test:admin
```

`test:admin` запускает отдельный локальный Vite :4174 с **фиктивным публичным ключом и сетевыми fixtures**. Это UI/контрактные тесты, а не доказательство реального Auth. `test:e2e` сохраняет регрессию публичного интерфейса. `test:database` требует изолированный PostgreSQL :55439 и тестовые роли anon/authenticated/service_role; hardcoded базы smok_stage1_test и smok_stage2_test пересоздаются в тестах. Никогда не направлять эти тесты на production. SQL-тесты реально проверяют права/транзакции/мутации и регрессию Guest RPC.

## Облачный acceptance test

1. Войти в `/admin/login` под созданным Admin, открыть Orders и Kitchen в двух окнах. Проверить refresh/logout.
2. В приватном окне `/admin/orders` должен требовать вход. Auth-пользователь без staff_profile должен получить отказ. Staff не должен иметь доступ к Menu/Settings.
3. Через публичный checkout создать тестовый заказ с комментарием `TEST — NIE PRZYGOTOWYWAĆ`. Сверить номер/итог/позиции в Supabase и обоих окнах кухни; появление — примерно за 5 секунд.
4. Пройти Przyjmij → Rozpocznij przygotowanie → Gotowe → Zakończ, проверить второе окно и refresh. Для отдельного теста проверить подтверждение отмены.
5. Отключить выбранный товар; через ≤15 с публичная кнопка должна стать Niedostępne. Отправка из старой корзины должна быть отклонена сервером. Вернуть исходную доступность.
6. Проверить изменение цены на согласованном тестовом товаре, новый серверный итог и неизменность старого заказа; вернуть исходную цену.
7. Отключить сеть, проверить заметную ошибку и восстановление. Проверить tablet 1024×768 / 768×1024.

Облачная проверка выполнена с локальной текущей версией: настоящая одноразовая Auth-сессия существующего пользователя (серверный generateLink + verifyOtp, без отправки письма и без изменения пароля), реальные PostgREST/RLS, все экраны, refresh/logout, реальный Guest Checkout, автоматическое появление заказа на кухне и статусы до отмены. Заказ `SMOK-100005`: две позиции, 241 zł, сохранён в статусе cancelled. Предыдущий тестовый заказ после ошибки селектора также отменён. Реальные заказы не менялись.

Запуск проверки (создаёт новый явно отмеченный тестовый заказ):

```bash
npm run dev -- --host 127.0.0.1 --port 4175 --strictPort
# Во втором терминале:
CONFIRM_CLOUD_ADMIN_TEST=true node scripts/verify-admin-cloud.mjs
```

Auth-токены остаются в памяти тестового процесса/изолированного браузера, не записываются в отчёт. Существующий правильный пароль не известен тесту: его ввод пользователем не проверен; проверены отказ при неверном пароле и реальная Auth-сессия через одноразовый токен.

Мутации menu/settings и ограничения staff/revoked проверены в облаке с откатом всех изменений:

```bash
supabase db query --linked --file scripts/verify-admin-rollback.sql
```

Транзакция всегда завершается ROLLBACK; сохранять временные изменения не нужно. Для финального публичного теста после согласованного deployment остаётся войти через `/admin/login` со своим существующим паролем. Публикация выполняется отдельным согласованным commit/push; текущий deployment проверяется по GitHub/Vercel. Этап 3 не начат.

Справочники: [Supabase password Auth](https://supabase.com/docs/guides/auth/passwords), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [API keys](https://supabase.com/docs/guides/getting-started/api-keys).

## Контроль после production deployment

```bash
CONFIRM_CLOUD_ADMIN_TEST=true ADMIN_TEST_BASE_URL=https://sushi-smok-szczecin.vercel.app node scripts/verify-admin-cloud.mjs
```

Этот режим использует строго разрешённый production origin, создаёт один новый отмеченный тестовый заказ и отменяет его. Auth/session значения не выводятся.
